# 00 — Development Requirements Specification

**Status key:** `CONFIRMED` = stated in the research package or by the project owner · `PROPOSED` = engineering recommendation requiring sign-off · `OPEN` = insufficient information, named owner must resolve.

This document answers the 28 questions from the Developer Handoff (Section 4), reconciling five prior research documents (*Business Problem Understanding and Decomposition*, *Feature Service Proposal*, *Production Architecture, Operationalization, and Rollout*, *Production Design*, *Technical Design and Research Report*, *Solution Design and Engineering Handoff Specification* — six files, five distinct research passes) into one coherent answer per question. Where documents disagreed, the resolution and its rationale are given; see `13-risks-and-dependencies.md` for anything left genuinely unresolved.

**Governing constraint (CONFIRMED, project owner, 2026-09-26):** this POC is **fully offline and local-only**. No hosted LLM APIs, no cloud storage/services, no external data sources. All notes, labels, and tabular demand history used anywhere in the POC are **synthetically generated by local code**. This constraint overrides any place in the source research that assumed a hosted API model was available.

---

## 1. What exactly are we building?

`CONFIRMED`. A **Demand Signal Feature Service** proof of concept: a local, batch-first pipeline that (a) generates synthetic qualitative business notes with known causal ground truth, (b) extracts structured demand-relevant events from those notes via a hybrid rules/NER/local-LLM pipeline, (c) validates and versions those events into an append-only signal ledger, (d) transforms them into point-in-time-correct forecasting features, (e) serves those features to a forecasting experiment, and (f) compares a tabular-only baseline forecast against a tabular+signal-enhanced forecast under a controlled, leakage-free, rolling-origin evaluation, with drift/monitoring mechanics demonstrated on seeded synthetic scenarios.

## 2. Why are we building it?

`CONFIRMED`. Current demand forecasting uses structured/tabular history only (e.g., shipments). Human-written commentary (account notes, service notes, supplier commentary) may contain information about future demand *before* it shows up in shipment history. If that information can be extracted reliably, made point-in-time correct, and served to the forecast, it may reduce forecast error. The POC exists to test that mechanism end to end under controlled conditions before any investment in real-data integration.

## 3. What business problem does it solve?

`CONFIRMED`. It targets four distinct losses identified in the business decomposition: **semantic loss** (prose isn't a numeric feature), **entity loss** (notes name customers/products loosely), **temporal loss** ("next quarter" isn't a forecast bucket), and **availability loss** (a valid signal extracted too late is useless to the forecast cycle it was meant to inform). The POC is designed to make each of these losses individually measurable rather than folding them into one "did the LLM work" question.

## 4. What hypothesis is the POC testing?

`CONFIRMED`. *"Qualitative information available before a shipment change may contain incremental predictive demand information; if it can be reliably extracted, represented without temporal leakage, and consumed by the forecast model, it can reduce forecast error versus a tabular-only baseline."* Explicitly **not** being tested: whether real company notes contain this information (synthetic data cannot establish that — see `01-poc-scope-and-non-goals.md`).

## 5. What are the input datasets?

`CONFIRMED` design, `PROPOSED` sizing. Six synthetic datasets, generated locally (see `06-synthetic-data-design.md` for full detail):

| ID | Purpose |
|---|---|
| D0 | Baseline synthetic tabular demand history (the forecasting target + existing structured covariates) |
| D1 | Synthetic note corpus (causally generated, for pipeline development) |
| D2 | Extraction gold/challenge set (independently hand-labeled, oversampled for hard cases) |
| D3 | Point-in-time joined forecast dataset (D0 + eligible D1/D2-derived signals per forecast cutoff) |
| D4 | Drift challenge set (seeded vocabulary/behavior/concept shifts) |
| D5 | Adversarial/safety challenge set (negation, contradiction, malformed/instruction-like text) |
| D6 | Reprocessing regression set (frozen notes re-run across extractor versions) |

## 6. What are the outputs?

`CONFIRMED`. (a) A versioned signal ledger (append-only structured events with evidence and provenance); (b) a point-in-time forecast-feature table; (c) baseline vs. enhanced forecast results with incremental-lift statistics and ablations; (d) an extraction-quality report (independent of forecast results); (e) a drift/monitoring demonstration report; (f) a lineage trace from any feature row back to its source note; (g) this documentation package itself as the pre-development artifact.

## 7. What is the canonical signal/data model?

`CONFIRMED`. Three layers, never collapsed: **source evidence** (what was written) → **structured signal** (machine interpretation, append-only, versioned) → **forecast feature** (model-ready aggregate/derived value). Full schema in `03-data-model.md` and `schemas/`.

## 8. What is the forecasting feature schema?

`PROPOSED`. A small, evaluation-driven initial family (presence/coverage, direction, magnitude, commitments/cancellations, timing, recency, confidence-weighted strength, source diversity, conflict indicator) — see `03-data-model.md` §Forecast Feature Layer. Fields are added only if an ablation shows they carry incremental value; nothing is retained by default.

## 9. What APIs/data contracts are required?

`PROPOSED`. For the POC: three JSON Schema contracts (evidence, signal, feature) validated locally via `jsonschema`/Pydantic; a callable local Python interface (not a network service) for the forecasting experiment to pull point-in-time features. A localhost-only thin HTTP layer is optional and only added if it's needed to demonstrate the "machine-consumable serving" requirement from the original brief — see `04-api-data-contracts.md`.

## 10. What components need to be built?

`CONFIRMED` (list), `PROPOSED` (grouping). See `02-architecture.md` and `05-technology-decision-matrix.md`: synthetic data generator; source/evidence store; extraction pipeline (rules → NER → local constrained-LLM → validator); signal ledger; feature transformation; feature access layer; forecast baseline; forecast experiment harness (4-arm); evaluation/metrics module; lineage recorder; drift/monitoring module. For the POC these are Python modules within one repository/process, not separate services (Non-Goal: no microservices — see `01-poc-scope-and-non-goals.md`).

## 11. What are the interfaces between components?

`PROPOSED`. In-process function calls and local file-based hand-offs (Parquet/DuckDB tables conforming to the JSON Schema contracts), not network RPC. Each stage reads/writes a versioned local table; nothing communicates through hidden shared mutable state. See `02-architecture.md` for the data-flow diagram.

## 12. What technologies are recommended for the POC?

`PROPOSED`, pending a local feasibility check for the LLM runtime. Python; spaCy (rules/NER); GLiNER (optional NER challenger); a small locally-hosted open-weight instruction model served via `llama.cpp`/`ollama`/local `transformers` with JSON-schema-constrained decoding (`outlines`/`llama.cpp` grammars) for the semantic-extraction stage; Pydantic + `jsonschema` for contracts; Pandera for tabular checks; Parquet + DuckDB (or SQLite) for storage; a conventional Python forecasting stack (e.g. `statsforecast`/`scikit-learn`/simple gradient boosting) for the baseline/enhanced models; pure-Python statistical drift checks (KS/chi-square; MMD/classifier-on-embeddings optional stretch). See `05-technology-decision-matrix.md` for the full per-component matrix and swap boundaries.

## 13. Which technologies are possible production alternatives?

`PROPOSED`/documented only, not built. Managed/self-hosted LLM serving at scale; Feast or a managed feature store; a warehouse/lakehouse with time-travel (e.g. Delta Lake) for the evidence/signal ledger; OpenLineage-based lineage; MLflow-based experiment/model registry; enterprise observability stack for drift alerting. See `05-technology-decision-matrix.md` "production alternative" column — none of this is implemented in the POC.

## 14. How will synthetic data be generated?

`CONFIRMED` (causal ordering), `PROPOSED` (implementation). A local generator produces: (1) a latent business-state trajectory per synthetic entity/product; (2) partial, plausibly-knowable-at-the-time information a synthetic "author" would have; (3) note text from that partial knowledge only (templated + randomized phrasing, including deliberately hard cases); (4) realized demand sampled *afterward*, independently, with noise and a nonzero "signal never materializes" probability. This ordering is the single most important anti-leakage discipline in the whole design — see `06-synthetic-data-design.md`.

## 15. How will signals be extracted?

`CONFIRMED` (hybrid approach), `PROPOSED` (implementation). Deterministic rules for quantities/units/known aliases → local NER for spans/entities → local constrained-decoding LLM for direction/negation/conditionality/temporal semantics → deterministic schema + business-rule validation, with abstention as a first-class valid output. See `07-extraction-pipeline-design.md`.

## 16. How will signals become forecasting features?

`PROPOSED`. A versioned SQL/Python transformation layer aggregates eligible signals (per the point-in-time rule) into windowed features (counts, decay-weighted scores, recency, magnitude aggregates) keyed by forecast entity and cutoff. Every transformation is pinned to a `feature_definition_version`. See `03-data-model.md` and `07-extraction-pipeline-design.md`.

## 17. How will features be served?

`PROPOSED`. Batch retrieval from local Parquet/DuckDB tables via a callable Python function (`get_features(entity_keys, cutoff, feature_set_version)`), returning values plus freshness/lineage metadata. An optional localhost HTTP wrapper may be added late if useful for demonstrating "machine-consumable" serving. No online/low-latency store — see Non-Goals.

## 18. How will lineage be maintained?

`PROPOSED`. Every signal and feature row carries immutable IDs for source revision, extractor version, prompt/rule-config version, schema version, and transformation version, stored alongside the row (not a separate lineage service for the POC). A lineage-trace utility resolves a feature row back to its source note. See `03-data-model.md` §Provenance and `12-implementation-milestones.md` Milestone 10.

## 19. How will freshness be measured?

`PROPOSED`. Explicit distinct timestamps (`source_event_time`, `available_at`, `extracted_at`, `feature_available_at`) are recorded on every record; freshness = `feature_available_at - available_at`. Since the POC is offline/batch (no live source stream), freshness is measured against the *simulated* arrival clock the synthetic generator assigns to notes, not wall-clock time. See `03-data-model.md`.

## 20. How will the forecasting experiment work?

`CONFIRMED`. A 4-arm rolling-origin comparison — (A) tabular baseline, (B) oracle signal features (from generator ground truth), (C) extracted signal features (real pipeline), (D) shuffled/time-shifted signal (negative control) — using identical tabular inputs, model, and hyperparameters across arms, evaluated only on observations after each forecast origin. See `08-forecasting-experiment-design.md`.

## 21. How will extraction quality be measured?

`CONFIRMED`. Independently from forecast results: macro F1 for event-type classification, field-level precision/recall (direction, magnitude, entity, temporal), evidence-grounding/unsupported-inference rate, abstention correctness, and a dedicated error taxonomy (false event, missed event, wrong entity, wrong direction, wrong magnitude, wrong timing, negation error, conditionality error, duplicate, stale signal, unsupported inference). See `09-evaluation-plan.md`.

## 22. How will forecast improvement be measured?

`CONFIRMED`. Relative error reduction of arm C (and B) vs. arm A on a predeclared primary metric (MASE), with MAE/bias as secondary, computed under rolling-origin CV, reported overall and on the signal-exposed subset, plus ablations isolating which feature families contribute value. See `08-forecasting-experiment-design.md` and `09-evaluation-plan.md`.

## 23. How will drift be detected?

`CONFIRMED`. Layered monitors across raw text/writing behavior, extraction behavior, feature distribution, feature↔demand relationship, and forecast performance, using statistical tests (KS/chi-square for univariate fields; embedding-distance/MMD as an optional richer test for text) calibrated on synthetic no-drift windows, with persistence-based alerting. Tested against deliberately seeded synthetic drift scenarios only. See `10-drift-monitoring-plan.md`.

## 24. How will the system be tested?

`CONFIRMED`. Unit/schema/contract tests, extraction gold-set tests (including hand-authored hard cases: negation, conditional, future-dated, reversal, uncertainty), point-in-time/leakage adversarial tests, feature-aggregation tests, forecast-experiment reproducibility tests, drift-calibration/false-alert-rate tests, and one end-to-end POC test. See `11-testing-strategy.md`.

## 25. What exactly must the POC demonstrate?

`CONFIRMED`. That the full pipeline mechanics work (schema validity, point-in-time correctness, lineage, reproducibility, drift detection) **and** that, under the controlled synthetic experiment, a deliberately planted early signal can be recovered and shown to add measurable forecast value versus the tabular baseline — while explicitly *not* claiming this holds for real company notes.

## 26. What is explicitly outside POC scope?

`CONFIRMED`. See `01-poc-scope-and-non-goals.md` — no real notes, no production infra (Kubernetes, streaming, online feature store, enterprise lineage/observability platforms), no automatic retraining, no multi-region, no network-facing service, no security/IAM implementation, no hosted/API models.

## 27. What would need to change for production?

`PROPOSED` (documented, not built). Real-data validation gate; classification/PII review of real notes; durable governed storage with retention/deletion policy; scaled extraction infra (still local or on-prem per the offline constraint unless that constraint is later relaxed); production SLOs for freshness/availability; human-review workflow; rollback/versioning discipline for extractor changes; business-approved forecast-lift threshold. See `13-risks-and-dependencies.md` and the "production alternative" columns throughout.

## 28. Which questions remain unanswered?

`OPEN`. See `14-open-questions.md` for the full register. Headline items: forecast grain/horizon/cadence/cutoff semantics (no real forecasting team input available); business-approved minimum meaningful forecast lift; exact local LLM/runtime that is actually installable in this environment (technology matrix proposes candidates pending a feasibility check); whether a localhost HTTP layer is worth building or a callable Python API suffices for this capstone's grading/demo needs.
