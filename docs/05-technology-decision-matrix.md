# 05 — Technology Decision Matrix

All choices below satisfy the confirmed **offline/local-only** constraint: no hosted APIs, no cloud services, no network egress required by any component. Everything must run on a single local machine (assume CPU-only unless a local GPU is confirmed available — `OPEN`, see `14-open-questions.md`).

| Component | POC choice | Why | Alternatives considered | Production alternative | Swap boundary |
|---|---|---|---|---|---|
| Language/runtime | Python 3.11+ | Matches the research's tooling recommendations (spaCy, Pandera, Pydantic, forecasting libs all Python-first) | R, Julia | Same, or polyglot services | N/A — whole POC is one language |
| Rule-based extraction | spaCy `Matcher`/`EntityRuler` | Deterministic, fast, CPU-only, transparent, good fit for quantities/units/known aliases | Plain regex | Same, hardened + expanded rule sets | Behind a common `extractor` interface (see `07`) |
| Statistical NER | spaCy statistical pipeline (local model download bundled/cached, not a live call) | Local, well-documented, integrates with rules in the same framework | GLiNER (local weights) as a challenger | Fine-tuned domain NER once real labels exist | Same interface |
| Semantic/complex extraction (negation, conditionality, direction, temporal) | A small locally-hosted open-weight instruction model (candidates: a 1–3B instruction-tuned local model runnable via `llama.cpp`/`ollama`/local `transformers`) with JSON-schema-constrained decoding (`outlines` or GBNF grammar) | Needed for the semantics rules/NER can't reliably capture; must run fully offline | Larger local models if GPU available; rules-only fallback if no model fits local compute | Managed/self-hosted LLM serving at scale, still subject to any future data-boundary policy | Behind the same `extractor` interface; degrades to rules+NER only if infeasible (see `07-extraction-pipeline-design.md` degradation path) — **OPEN: exact model/runtime pending a local feasibility check** |
| Contract validation (records) | Pydantic + `jsonschema` | Pure Python, no service, matches the three schema files exactly | Manual dataclass validation | Schema registry (Confluent-style) if scaled | Contracts are the swap boundary already |
| Tabular/feature-table validation | Pandera | Declarative dataframe checks, integrates with pandas/DuckDB output | Great Expectations | Great Expectations or a central DQ platform | Wraps the same Parquet/DuckDB tables |
| Raw/signal/feature storage | Parquet files + DuckDB (SQLite acceptable fallback) | Local-only, zero server process, supports SQL joins needed for point-in-time logic, trivially versioned by directory/partition | Plain CSV/JSON, SQLite only | Governed warehouse/lakehouse with time-travel (e.g. Delta Lake) | Storage is read only through the feature-access layer's functions — swapping the backend doesn't change callers |
| Point-in-time join logic | Hand-written SQL/DuckDB queries implementing the eligibility rule directly | Avoids operating a full feature-store product for a POC; the *pattern* (not the product) is what matters | Feast (local mode) | Feast / managed feature store, if complexity later justifies it | Encapsulated entirely inside `get_historical_features` |
| Feature serving | Callable Python function; optional localhost-only FastAPI | No network dependency required; matches offline constraint | gRPC service | Feature-store-native serving layer, or an internal API gateway | The function signature in `04-api-data-contracts.md` is the boundary |
| Forecasting models (baseline + enhanced) | Conventional local Python forecasting (e.g. `statsforecast`/`scikit-learn`/gradient boosting), run identically across all 4 arms | Keeps the experiment about the *features*, not the *algorithm*; no GPU/cloud training needed | Deep learning forecasters | Whatever the company's actual forecasting platform is (unknown — `OPEN`) | Model choice is orthogonal to the feature contract |
| Drift detection | Pure-Python statistical tests (KS/chi-square) on numeric/categorical fields; optional local sentence-embedding model for text-semantic drift, run locally (no hosted embeddings API) | Cheap, interpretable, offline-compatible | Alibi Detect (verify local-only usage and license terms before adopting) | Alibi Detect / enterprise ML-observability platform | Detector functions consume the same feature/extraction tables; swappable independently |
| Experiment tracking / reproducibility | Flat versioned config + result files (JSON/YAML per run, named by run ID) written locally | No server process needed for a POC of this size | Local MLflow instance (still offline, but adds a service to run) | MLflow / managed experiment tracking | Run artifacts are just files; a tracking tool can ingest them later without changing how they're produced |
| Lineage | Provenance columns embedded directly in signal/feature rows (see `03-data-model.md`) + a local lineage-trace utility function | No lineage service needed at this scale | OpenLineage events written to a local log file | OpenLineage-compatible lineage backend | The lineage-trace function is the boundary; it can be reimplemented against a real lineage store later without changing row-level provenance fields |
| Testing | `pytest` + `hypothesis` (property-based tests for schema/temporal invariants) | Standard, local, no service dependency | — | Same | N/A |

## Open items in this matrix

- **Local LLM/runtime pick** — `OPEN`. Needs a quick feasibility check (can a 1–3B instruction model run acceptably on the available machine?). Until confirmed, `07-extraction-pipeline-design.md` treats the LLM stage as optional/degradable.
- **GPU availability** — `OPEN`. Affects only how large a local model is practical; does not affect the architecture.
- **Whether the localhost HTTP wrapper is worth building** — `OPEN`, low-stakes; default is "callable Python API is sufficient," HTTP wrapper added only if there's a specific reason (e.g. a grading rubric requirement) to demonstrate an API surface.
